# Operations track: traced, resumable, unattended runs (added 2026-10-29)

(Called "Phase 1" in the Oct 25 four-phase plan; named the operations track here because docs/plan.md already uses Phase 1–6 for the delivered runtime phases.)

Why: the service answers one question per request and forgets it. `/query` is single-shot and never touches `agent_graph`; the graph runs only in `eval_harness --graph` and its demo. `cost_tracker.record` covers `/query` alone, and the runtime's `AuditLogger` is never attached on the service path, so the deployed agent writes no audit log. Nothing records what the graph did step by step, a run that dies mid-way cannot be picked up, and nothing runs without a person at the keyboard. Phase 1 adds those three things with the smallest surface that fits the existing code: the approval graph already uses `SqliteSaver`, cost tracking already writes `logs/planner_metrics.jsonl`, and the eval harness already knows how to run the graph headless.

The hard rules stay: every SQL still goes through `sql_guard`, SELECT-only, PHI redaction intact, no keys in code, schema and planner change together. Each item is one PR with tests and eval cases.

| # | Item | How |
|---|---|---|
| **O1** | **Run tracing.** Every planner run gets a `run_id`; every node, model call, guard verdict and query execution is a span, persisted and queryable | `trace.py`: a `Tracer` with `span(name, **attrs)` as a context manager and a `contextvars` current-run, writing one row per span to `logs/traces.sqlite` (`runs` and `spans` tables: run_id, span_id, parent_id, name, started_at, ended_at, status, attrs JSON) and mirroring to `logs/traces.jsonl`. `agent_graph.py` opens a run span in `run()` and a span per node; `nl_to_sql_planner.py` wraps each provider call (provider, model, tokens, latency, cost from `cost_tracker`); `sql_guard` records the verdict and the SQL hash, never the redacted values. The same tracer wraps `/query` (single-shot) and `/propose` (approval graph), so every path is traced, and `app.py` attaches the existing `AuditLogger` to its `AgentRuntime` (today it is only used by the demo scripts; `aiops_metrics.load_events` is pointed at the directory it actually writes to). `app.py` gets `GET /runs` (latest N) and `GET /runs/{run_id}` (the span tree); the UI Usage view lists recent runs and opens one. No OpenTelemetry dependency; an OTLP exporter is a later adapter over the same table |
| **O2** | **Checkpointed planner runs.** The planner graph compiles with a checkpointer, so a run can be inspected after the fact and resumed after a failure | `agent_graph.py` `_build()` compiles with `SqliteSaver` on `CHECKPOINT_DB` (the file the approval graph already uses), `thread_id = run_id`. `run()` takes an optional `run_id` to resume: `get_state` shows where it stopped, `invoke(None, config)` continues from the last checkpoint. A new `POST /runs` endpoint runs a question through the checkpointed graph (self-correcting path) and returns `run_id` plus the answer; `/query` stays single-shot and unchanged, so the eval gates are untouched. `GET /runs/{run_id}/state` returns the checkpoint summary (node, attempts, last_error, trajectory). `python agent_graph.py --resume <run_id>` for the CLI. Tests: a run interrupted after `plan` (a fake planner that raises on the second call) resumes and finishes with the same `run_id` and no second model call for the first step |
| **O3** | **Unattended scheduled runs.** Standing questions run on a schedule with a budget, record their answers, and raise an alert on failure or drift | `schedules.yaml` at the repo root: named questions with a cadence, dataset (`hospital` or `fhir`), and a per-run cost cap. `scheduled_runs.py` runs each through the graph headless (the `eval_harness` pacing and provider code reused), records `(schedule, run_id, result_hash, rows, cost, status)` in `logs/scheduled_runs.sqlite`, and compares the result hash with the previous run: a changed hash is `drift`, a guard denial or exception is `failed`. Exit code 0 ok, 1 failed, 2 provider unavailable, as the eval harness does. `.github/workflows/scheduled-runs.yml` runs it weekly on Gemini (free tier, `PLANNER_MIN_INTERVAL_SEC=5`), uploads the results, and on `failed` or `drift` opens or updates one issue titled `scheduled run: <name>`. `GET /scheduled` lists the last result per schedule for the UI |
| **O4** | **Evals and write-up** | Eval cases for the four standing questions in `schedules.yaml` (they are ordinary eval cases first, so the schedule never runs a question the suite does not already pass). README section "Runs, traces and schedules". CLAUDE.md architecture bullets updated in the same PRs |

**Out of scope for this track.** Phase 2 (sandboxed code runner, file tools, the MCP server as a Claude Code client, the demo rebuild) and Phase 3 (the orchestrator on the data intake platform) follow in sequence. Streamable HTTP for the MCP server stays on the roadmap as item 4.

**Render.** The service disk on Render is ephemeral, so `logs/*.sqlite` resets on each deploy; traces and checkpoints there are per-deploy. That is acceptable for the demo; a Render disk or Postgres is the upgrade if persistence across deploys is wanted later.

**Order.** O1, O2, O3, O4. O1 and O2 run in CI without a key (`pytest`); O3's workflow needs `GEMINI_API_KEY`, which CI already has for the eval gates.
