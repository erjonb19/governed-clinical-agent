Guide

Which dataset to ask, and how to ask it.

Step 1 — choose the right dataset

These are two separate bodies of data. A question about patients cannot be answered by hospital data, and vice versa.

Hospital quality

U.S. hospitals · public CMS data · refreshed monthly
Contains: star ratings, 30-day readmission rates, Medicare spend per patient, emergency-department wait and boarding times, by facility and state.
Ask about: facilities, quality, cost, geography.
  • Which hospitals have the worst readmission rates?
  • Best value: high quality, low cost?
  • Longest psychiatric ED boarding times?
Cannot answer: anything about individual patients, diagnoses, medications or lab results.

Clinical records

1,180 patients · ~331,000 records · synthetic (no real PHI)
Contains: patients, encounters/visits, diagnoses, medications, procedures and lab observations.
Ask about: patients, conditions, treatments, utilisation.
  • How many patients by gender?
  • How many distinct patients have viral sinusitis?
  • Most frequently prescribed medications?
Cannot answer: hospital ratings, readmission rates or facility costs.
Ask the wrong one and nothing breaks — you’ll get a Can’t answer card with a one-click button to switch and retry.
Step 2 — question or SQL?

Question recommended

Type plain English. The assistant writes the query for you. Use this unless you specifically want to write SQL.

“Which hospitals give the best value?”

SQL

For analysts who know the tables. You write the query; the security layer still checks it before it runs.

SELECT facility_name, star_rating FROM gold_hospital_profile LIMIT 10

The column names are on the Data tab, under “Full data dictionary”.
Step 3 — where should it read from?

This computer — a local database file. Fast, no cloud, always available.

Databricks cloud — the same tables in your cloud warehouse. Identical answers and identical security; the first query may take a moment while the warehouse wakes up.

Why you can trust the answers

The assistant proposes; an independent security layer decides.

  1. You ask a questionIn plain English — no query language required.
  2. A model drafts the queryWritten against a fixed, published data dictionary. It cannot invent tables or columns.
  3. The security layer rules on itRead-only, approved tables only, automatic result limits, no system or file access. Anything else is refused at the boundary — with the reason shown.
  4. You get the answer and the receiptThe result, the exact query that ran, and what the request cost.
Guarantees
Read-only

Data can never be modified or deleted.

Approved tables only

Access outside the allow-list is refused.

Result limits

Bulk extraction is capped automatically.

Fully audited

Every decision is recorded and reviewable.

See it yourself: on the Ask tab, switch Mode to SQL and run SELECT * FROM information_schema.tables. It is valid SQL, and it is still refused — because it reaches into the system catalog. Ask the same thing in plain English and you see the other half of the design: the assistant declines up front, because the data dictionary it was given contains no such table.
